# 使用 BunnyBook

BunnyBook 是课程设计的信息源，不是替教师作最终教学判断的自动编课器。插件是第三方本地测试版，并非 Kimi 官方插件。

## 必守边界

- 只调用 BunnyBook 的读取类 MCP 工具；不得写回本体、改写图谱或把 Agent 输出伪装成图谱原始数据。
- 保留主题 ID、节点 ID、`prerequisite_id -> topic_id` 关系方向、`source_ref`、`review_status` 与核心素养 ID。
- 明确区分两层事实：课标科目、核心素养名称及其来源指针；BunnyBook 作者提出、仍需人工复核的主题、节点、先修关系和课标映射。
- 不得声称项目映射是课标直接规定，不得声称当前覆盖等同于全部国家高中课标，也不得把未复核映射表述为专家共识。
- 课程活动的适龄性、学情、时间、安全、伦理和评价可行性必须由教师最终确认。

## 设计活动的默认流程

1. 先调用 `get_source_overview`，读取版本、数量、关系方向与信任边界。
2. 如果用户没有给出有效主题 ID，调用 `list_themes` 或 `search_curriculum` 提供少量匹配主题，并让教师选择；不要凭标题猜 ID。
3. 主题确定后，调用 `build_activity_context`。把用户给出的年级、课时、班额、设备、材料与其他限制写入 `learner_context` 和 `constraints`。
4. 需要核查单个节点或学习顺序时，调用 `get_topic_context`、`get_theme_context` 与 `trace_learning_path`。
5. 完成草案后调用 `validate_references`，确认草案中的所有稳定 ID 都存在。
6. 输出活动方案时至少包含：驱动问题、最终作品或表现任务、学科贡献、活动阶段、评价证据、来源 ID、待教师复核项。

## 教师草案的默认成品形态

- 只设计一个活动，不列 A/B/C 多套通道，也不先输出节点元数据说明书。
- 若教师没有给出班情，明确采用“高一、90 分钟、40 人、4—5 人小组”的试用假设，本轮不先追问。
- 默认把 90 分钟活动视为最终表现任务的一次单课切片：当堂只完成一个共同中间成果，不得把数周项目压缩成“已经完成”；上下文未提供的 `hard` 前置列为课前假设或教师需确认。
- 正文顺序固定为：活动概览 → 学科如何共同工作 → 90 分钟流程 → 怎样判断学生学会了 → 依据与复核。
- 每门学科必须为同一个共同成果提供不同的概念、证据或方法，不能拆成互不相干的小作业。
- 上下文中已经提供且适合当堂调用的 `hard` 前置进入流程；未提供的 `hard` 前置不得伪装成已完成，应列为课前假设或教师需确认；`soft` 前置只是建议脚手架。
- ID、`source_ref` 和 `review_status` 集中放到末尾精简表格；正文先让教师看到课堂价值和学生行动。
- 完整证据对象只在用户明确要求“核对依据、调试或返回 JSON”时展开。
- 公开分享的活动应附上 BunnyBook 图谱返回的许可署名。

## 审查证据的默认流程

1. 对 ID 直接调用对应的主题或节点上下文工具；对自然语言先调用 `search_curriculum`。
2. 把课标科目、核心素养、内容单元、`source_ref`、内容锚点和复核状态并排呈现。
3. 如果证据只支持“项目映射”，就这样标注；不要把它升级为“课标要求”。
4. 发现未知 ID 时，用 `validate_references` 报告，不自行补造。
